# Ответ на ревью Евгения

> Документ фиксирует решения по 11 замечаниям после ознакомления Евгения с документацией проекта.
> Все принятые решения отражены в `PROJECT.md` и `docs/IMPLEMENTATION_PLAN.md`.
> Если по какому-то пункту возражение — правь прямо здесь, обсудим.

---

## 1. Распределение задач — гибрид тендер → round-robin

**Замечание:** round-robin не учитывает мотивацию в моменте; чистый тендер даёт лучшую мотивационную динамику.

**Решение:** гибрид. Задача сначала публикуется в общий канал ассистентов на 5–10 минут — первый кто откликнулся, забирает. Если за окно никто не взял — fallback на round-robin с таймаутом (как было).

**Почему гибрид, а не чистый тендер:** при чистом тендере риск что быстрые ассистенты заберут всё, средние/новые останутся без работы → выгорание у одних и отток у других. Гибрид даёт мотивацию быстрым и страховку для остальных.

**В плане:** фаза M10 (Распределение задач) — 6ч. Окно тендера хранится в `policies.config.tender_window_minutes` в Neon — можно крутить от 5 до 10 минут по результатам.

## 2. Карточка задачи — добавлены 2 поля

**Замечание:** в карточке задачи не хватает «конечный результат» и «контекст и материалы».

**Решение:** в M7 (Создание задачи `/newtask`) карточка становится полной:
- `text` — текст задачи
- `acceptance_criteria` — критерий приёмки
- `expected_result` — **новое**, как выглядит готовая работа
- `context_materials` — **новое**, что уже есть у заказчика
- `time_limit` — лимит часов
- `deadline` — дедлайн

Без двух новых полей `/newtask` не завершается — валидация обязательна.

---

## 3. Шаблон отчёта pre-start — добавлен

**Замечание:** до начала работы полезно зафиксировать структуру выхода — это страхует на случай передачи задачи или доработки.

**Решение:** отдельная фаза M8 (2ч). После `/accept` задачи и до `/start_work` ассистент обязан прислать free-form описание структуры результата (таблица, список, схема — формат свободный). Без этого `/start_work` не запускается. Сохраняется в `task_assignments.pre_start_plan`.

---

## 4. Сценарии поведения для код-задач — обязательный артефакт сдачи

**Замечание:** при сдаче кода без сценариев «X → Y» проверять субъективно и долго.

**Решение:** отдельная фаза M9 (2ч). Для задач с типом `code` при `/done` ассистент обязан приложить сценарии в формате «пользователь делает X → система отвечает Y». Без сценариев `/done` отклоняется. Накопленные сценарии — основа для регрессионного тестирования в R-фазе.

---

## 5. Оплата по факт-часам — заменена на оплату по лимиту

**Замечание:** оплата по факт-часам стимулирует работать медленнее.

**Решение:**
- **Оплата = `time_limit` × `rate_по_грейду`.** Фиксированная сумма, известная ассистенту заранее.
- Факт-часы (`/start_work` / `/pause` / `/done`) фиксируются в `task_assignments.actual_hours` — **только для аналитики**, не для оплаты.
- **Апелляция лимита:** до `/start_work` ассистент может **1 раз** запросить пересмотр лимита с обоснованием. Модератор (Дмитрий/Александр) меняет лимит или отказывает.

**В плане:** фаза M11 (Оплата + апелляция + возвраты + не-сдачи) — 7ч. Коэффициенты и правила читаются из `policies.retry_policies` в Neon.

## 6. Что если не сдал в срок — правило зафиксировано

**Замечание:** без явного правила реальная нагрузка будет давать прецеденты.

**Решение:**
- После `deadline` запускается grace-период **2ч** (значение в `policies.config.deadline_grace_minutes`).
- Если по истечении grace результата нет — задача автоматически возвращается в очередь распределения, текущему исполнителю оплата = **0**, событие пишется в `audit_log`.
- Счётчик `failed_deadlines_this_month` в карточке ассистента инкрементируется.
- При значении **3 за месяц** (значение в `policies.config.failed_deadline_pause_threshold`) ассистент уходит на паузу с пересмотром грейда модератором.

---

## 7. Оплата при доработке — правило зафиксировано

**Замечание:** без зафиксированного правила каждый случай будет решаться вручную.

**Решение** (хранится в `policies.retry_policies`):

| Номер доработки | Множитель оплаты | Действие |
|----------------|-----------------|---------|
| 1-я доработка | × 1.0 | Полная оплата после финального принятия |
| 2-я доработка | × 0.8 | −20% от лимита |
| 3-я доработка | transfer | Задача переходит другому исполнителю с **полной** оплатой ему |

Возврат с типом ошибки `mismatch_tz` или `critical` (см. п. 9) **дополнительно** сбрасывает счётчик грейда (см. п. 10).

---

## 8. Контроль качества — peer-review lite в MVP

**Замечание:** между «нет проверки» и «полная взаимопроверка из R1» — пропасть. Нужно минимальное решение.

**Решение:** новая фаза M12 (8ч) — **peer-review lite**. Без 4-х документов, без судьи (это всё R1 в Развитии II), но проверка перед отправкой к Дмитрию/Александру обязательна.

**Схема:**
1. Ассистент A сдал задачу через `/done`.
2. Бот выбирает ассистента B — не A, свободного, не тот кто давал апелляцию по лимиту.
3. B получает уведомление с задачей + результатом + чек-листом 5–7 пунктов (читается из `policies.config.peer_review_checklist`):
   - Критерий приёмки выполнен?
   - Сценарии «X → Y» работают (для код-задач)?
   - `expected_result` соответствует факту?
   - Оформление в норме?
   - Использованные материалы соответствуют `context_materials`?
4. B жмёт «ок» или «есть замечания» + указывает тип ошибки (из 4-х типов, см. п. 9).
5. Если «ок» — пакет идёт Дмитрию/Александру на финальное принятие.
6. Если «замечания» — возврат A на доработку с правилами из п. 7.
7. **Оплата B:** фикс **50₽** за каждую проверку (значение в `policies.config.peer_review_pay_rub`).

## 9. Типизация ошибок — справочник на 4 типа

**Замечание:** без классификации проверка субъективна.

**Решение** (хранится в таблице `error_types` в Neon, читается кодом и ИИ-агентами одинаково):

| Тип | Что значит | Влияет на оплату | Влияет на счётчик грейда |
|-----|-----------|-----------------|--------------------------|
| `format` | Оформление, орфография, форматирование | Нет | Нет |
| `incomplete` | Не все пункты ТЗ выполнены | Доработка по правилу из п. 7 | Нет |
| `mismatch_tz` | Не соответствует ТЗ принципиально | Доработка + при 3-й — переход | **Да** (сброс) |
| `critical` | Критичная ошибка (баги, потеря данных, нарушение ТК/ПДн) | Возврат, оплата 0 | **Да** (сброс + минус в историю) |

Используется и в фазе M6 (дашборд оценки), и в M12 (peer-review).

## 10. Переходная рейтинговая система — грейды

**Замечание:** до запуска D4 все на одной ставке = хорошие уходят.

**Решение:** документ-договорённость с первого дня MVP, хранится в таблице `grades` в Neon (структура готова к подключению D4 авто-пересмотра ставки):

| Грейд | Ставка | Условия перехода |
|-------|--------|------------------|
| **Junior** | 200 ₽/ч | Стартовая для всех новых ассистентов |
| **Middle** | 250 ₽/ч | 10 принятых задач без возврата `mismatch_tz`/`critical` **И** ≥2 недели в команде |
| **Senior** | 300 ₽/ч | 30 задач всего **И** ≥1 месяц в статусе Middle |

**Сброс счётчика:** возврат с типом `mismatch_tz` или `critical` обнуляет счётчик «задач без возврата». Это создаёт стимул к качеству, а не к скорости.

**Кто считает в MVP:** Дмитрий/Александр раз в неделю смотрят сводку и руками меняют `assistants.grade` через команду в боте. После запуска D4 (Доработка I) — автоматически.

## 11. Критерии перехода фаз — числа

**Замечание:** без триггеров доработки останутся бессрочно «в планах».

**Решение** (фиксируется в `IMPLEMENTATION_PLAN.md`):

| Фаза | Триггер запуска |
|------|----------------|
| **D1** — ИИ-оценщик тестов | Поток ≥10 кандидатов в неделю |
| **D2** — Личный кабинет ассистента (`/me`) | После D1, без отдельного триггера |
| **D3** — Шаблонные нотификации | По запросу Дмитрия/Александра |
| **D4** — Авто-пересмотр ставки | ≥6 активных ассистентов |
| **D5** — Карточка кандидата для коммуникатора | После D1 |
| **D6** — Умное распределение | ≥10 ассистентов |
| **R1** — Полная взаимопроверка (4 доки, судья) | ≥10 ассистентов **ИЛИ** Дмитрий/Александр тратят >2ч/день на проверку |
| **R2** — Manager Hub | По запросу Дмитрия/Александра |
| **R3** — Multi-brain агенты | После D1 + R1 |
| **R4** — Прод VPS | Первый клиент-заказчик готов платить |
| **R5** — Веб-дашборд | ≥15 ассистентов |

Триггеры хранятся в `policies.config.phase_triggers` — можно подкорректировать без перевыпуска документов.

## Дополнительное архитектурное решение: правила в Neon с первого дня

**Не было в замечаниях Евгения, но критично:** все настраиваемые правила (грейды, типы ошибок, коэффициенты доработки, окно тендера, grace-период, чек-лист peer-review, триггеры фаз) хранятся в Neon Postgres с первого дня MVP, **а не хардкодом в коде или env-файле**.

**Почему:** проект предполагает multi-brain ИИ-агентов в Доработке I и Развитии II (D1, D4, R1, R3). Если правила в коде — каждый ИИ-агент будет дублировать их в промпте, рискуя рассинхроном с детерминированной логикой. Если правила в Neon — и код, и ИИ-агенты читают из одного источника.

**В плане:** фаза M2 (Схема БД) включает таблицы `grades`, `error_types`, `retry_policies` и общую `config` + seed-миграцию с дефолтами. +1ч к M2 (6ч вместо 5ч).

## Что обсудить если будут вопросы

- Размер оплаты peer-review (50₽) — может быть мало для качественной проверки.
- Пороги грейдов (10/2 нед, 30/1 мес) — Евгений как ближний к живым кандидатам может предложить более реалистичные.
- Список критериев в чек-листе peer-review — финализировать до старта M12.
- Окно тендера 5–10 мин — подкрутить после первого пакета задач.
