# Autoeval — автопроверка курса-теста для бизнес-ассистентов

Механизм автоматической проверки 9 задач курса-теста на тему «настройка ИИ-среды».
Описание задач: [`../hr-tasks/final.html`](../hr-tasks/final.html).

## Что это

- **9 задач** в `tasks/NN-slug/`. Каждая независимая, со своим скрытым тест-сетом.
- **Шкала 10/10:** 6 баллов автопроверка (промпт кандидата прогоняется через `promptfoo` на скрытых кейсах) + 4 балла LLM-судья по логу процесса.
- **Стек:** Node.js + [promptfoo](https://promptfoo.dev) + OpenRouter (любая модель Claude/GPT/Gemini).
- **Локально:** проверяющий держит механизм на своём ноутбуке. Папка `tasks/*/hidden/` — в `.gitignore`, кандидаты её не видят.

## Установка (5 минут)

```bash
cd autoeval
npm install
cp .env.example .env
# Открой .env и вставь OPENROUTER_API_KEY=sk-or-v1-...
```

Готово. `promptfoo` уже подтянулся в `node_modules`.

## Как проверить одну сдачу

Кандидат прислал сдачу — например, файл `submission-anna-task01.md`. В нём ДВЕ обязательные секции:

```markdown
### ФИНАЛ
<финальная конфигурация — промпт / правила / контекст-пак — то что кандидат отдал как лучший вариант>

### ЛОГ
<лог процесса: ≥3 версии с пояснением, какие замеры толкнули к правке.
ИЛИ — если результат отличный с одной попытки — обоснование почему хватило.>
```

Запуск:

```bash
npm run eval -- --task 01 --submission ../submissions/anna/task01.md
```

> **Важно по поводу ключа:** `eval.mjs` загружает `OPENROUTER_API_KEY` из `autoeval/.env` и **перезаписывает** одноимённую системную переменную, если она есть. Это специально — чтобы ключ из проекта (autoeval) не путался с ключом другого проекта (OpenClaw, основной assistant-hub).

Что произойдёт:

1. Скрипт распарсит сдачу, найдёт блок `### ФИНАЛ` и `### ЛОГ`.
2. Финал-блок запишется в `tasks/01-*/_submission_prompt.txt` (плейсхолдер для promptfoo).
3. `promptfoo eval` прогонит этот промпт на всех скрытых кейсах задачи 1 → выдаст % пройденных.
4. LLM-судья оценит лог по 4 пунктам (бранч «защита одной попытки» сработает автоматически, если результат ≥5/6 и лог короткий).
5. На экране — разбивка `X.X/10`. Отчёт сохранится рядом со сдачей в `.report.json`.

Время одной проверки: 3-7 минут (зависит от размера тест-сета).

## Как отдать задание кандидату

1. Открой `tasks/NN-slug/task.md` и `tasks/NN-slug/training/`.
2. Скопируй содержимое в Google Doc / Notion / PDF — что удобно.
3. Не давай папку `hidden/` (там эталоны и тест-сет).
4. Отправь кандидату ссылку. Срок — на твой выбор.

## Калибровка перед боевым запуском

ОБЯЗАТЕЛЬНО: до того как давать реальным кандидатам — прогони 1-2 «эталонные» сдачи через `npm run eval`. Это покажет:

- разброс баллов адекватный (сильная сдача >7, слабая <5)
- никаких ошибок в yaml / промптах / провайдере
- LLM-судья выдаёт осмысленные оценки

Если разбросы кривые — правь:
- `tasks/NN/hidden/tests.yaml` (ассерты)
- `scripts/judge.mjs` (промпт судьи)

## Известные ограничения v1

- **Задача 5 (контекст-пак) — baseline-схема:** механизм поддерживает оба прогона через два конфига (`promptfooconfig.yaml` + `promptfooconfig.baseline.yaml`), но дельта-арифметика сейчас не автоматизирована — считать вручную (см. `tasks/05/hidden/README.md`).
- **Задача 8 (автопромптинг) — двухслойная проверка:** в v1 упрощённая — оцениваем структуру сгенерированного промпта через `llm-rubric` (RICECO-проверка). Полноценная двухслойная (где сгенерированный промпт реально гоняется на втором тест-сете) — TODO.
- **LLM-судья** не идеален — есть погрешность. Это закрывает рубрика из 4 бинарных пунктов (минимизирует субъективность).
