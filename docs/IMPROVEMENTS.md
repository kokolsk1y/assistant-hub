# IMPROVEMENTS — где можно сильно улучшить

Аудит текущей концепции платформы. Цель — найти места где можно сделать существенно сильнее того что описано в исходных документах.

Каждое улучшение оценено: **Импакт** (низкий/средний/высокий) × **Сложность** (низкая/средняя/высокая) × **Когда** (MVP / v1.5 / v2 / Future).

---

## ⭐⭐⭐ ГЛАВНАЯ АРХИТЕКТУРНАЯ ИДЕЯ — Proxy-коммуникации

> *Источник: Коля, по аналогии с Midjourney в Discord*

**Все коммуникации проходят через платформу.** Дмитрий не пишет в личку ассистенту напрямую — он пишет **через дашборд / специальный бот для управленцев**, платформа доставляет адресатам с правильным форматированием.

```
Кандидаты/Ассистенты  →  TG-бот ассистентов  ←→  ПЛАТФОРМА  ←→  Дашборд для управленцев  →  Дмитрий
                                                     │
                                                  Audit Log
                                                  Шаблоны
                                                  Метрики
                                                  История
```

**Что это даёт:**

1. **Дмитрий работает в одном месте** — дашборд с дёргалками:
   - Все ассистенты с их рейтингом и текущей загрузкой
   - Все задачи (открытые / в работе / на ревью / закрытые)
   - Часы за неделю, готовые сводки для выплат
   - Очередь кандидатов на созвон
   - История взаимодействия с конкретным ассистентом

2. **Никаких «закулисных договорённостей»** — если Дмитрий хочет назначить ассистенту созвон, он не пишет ему в TG личку. Жмёт в дашборде «назначить созвон» → бот шлёт ассистенту красивую карточку с кнопкой «Подтвердить».

3. **Полный audit trail** — каждое действие записано, ничего не теряется

4. **Шаблонизация** — Дмитрий не пишет руками одинаковые сообщения. Платформа берёт шаблон + данные → формирует и шлёт.

5. **Многоканальность** — будущее: добавить WhatsApp, Email, Discord — изменится только канал доставки, логика та же.

6. **Безопасность** — если ассистент уходит, у него нет «личных контактов» Дмитрия. Каналы закрываются с одной кнопки.

**Аналогия — Midjourney в Discord:**
В Discord нельзя «попросить MJ что-то сгенерировать в личке». Только через `/imagine` в канале. Все видят процесс, все метаданные сохранены, можно повторить, можно посмотреть историю. То же самое — но приватнее (личные каналы вместо публичных).

**Что это значит для разработки:**

- Дашборд = **обязательная часть MVP**, не v1.5
- Нужен интерфейс для управленцев: либо отдельный TG-бот, либо web-dashboard
- **Рекомендация:** на старте — отдельный TG-бот «Manager Hub» (быстрее сделать). Web-dashboard — v1.5 или v2.

**Размер новой задачи:** +15-20 часов к плану (новая Фаза 4.5 "Manager Hub bot").

**Это переводит улучшение #1 (self-service) и #3 (карточка коммуникатору) из «приятно иметь» в «обязательно».**

## 🏆 ТОП-7 главных улучшений (по соотношению импакт / сложность)

### 1. Self-service кабинет ассистента в боте

**Импакт:** высокий | **Сложность:** низкая | **Когда:** MVP

Каждый ассистент через бота может в любой момент посмотреть:
- 📊 Свои метрики (скорость отклика, доля принятых, рейтинг)
- 💰 Сколько заработал за неделю / месяц
- 📈 Динамика рейтинга — растёт / падает
- 🎯 Что улучшить чтобы повысить ставку («осталось 2 задачи без замечаний для +20₽»)
- 📅 График на эту неделю и согласованные окна

**Почему важно:** В документах работа полностью «push» (бот шлёт задачи), у ассистента нет инициативы. Дашборд = чувство контроля над своим ростом. Снижает выгорание, увеличивает мотивацию.

**Реализация:** команды `/me`, `/stats`, `/money`, `/grow`. Часы и метрики уже есть в БД — нужен только UI вывода.

---

### 2. Прогресс-бар «до повышения ставки»

**Импакт:** высокий | **Сложность:** низкая | **Когда:** MVP

Геймификация роста. После каждой принятой задачи бот пишет:
> ✅ Задача принята. До повышения ставки осталось 2 задачи без замечаний.
> ▰▰▰▱▱ 3/5

Текущий механизм пересмотра — раз в неделю «управленец смотрит». Заменяем на постоянный прогресс с понятной целью.

**Почему важно:** Размывает «недельные качели» — ассистент понимает что каждая задача приближает к росту.

**Реализация:** правило роста (4/5 принятых = +20₽) → счётчик в БД → сообщение после сдачи.

---

### 3. Карточка кандидата для коммуникатора

**Импакт:** высокий | **Сложность:** средняя | **Когда:** MVP

Когда кандидат уходит «на созвон», коммуникатор получает не просто «созвонись с Васей», а **готовую сводку**:

```
👤 Василий Иванов  @vasya_username
📥 Источник: src_presentation_v1, пришёл 22 мая
📋 Анкета: направление — вайбкодинг, уровень middle, опыт с ИИ — confident

🧪 Тестовое отборочное: 45/100 (пограничный)
   ✅ Хорошо: формулирует промпты конкретно
   ⚠️ Слабо: не заметил баг в ответе ИИ, не докрутил итог
   💬 Кандидат сам отмечает: «впервые делал такое, нужна была бы помощь»

🎯 Что обсудить на созвоне:
   - Готов ли учиться / есть ли время на развитие
   - Опыт самопроверки (умение замечать ошибки)
   - Какие задачи ему интересны
```

**Почему важно:** Без сводки коммуникатор тратит 15 мин на «расскажи о себе». Со сводкой — сразу глубокий разговор.

**Реализация:** ИИ-агент склеивает анкету + результаты теста + цитаты + предлагает темы. Чисто LLM-задача, без сложной БД-логики.

### 4. AI-наставник для задач

**Импакт:** высокий | **Сложность:** средняя | **Когда:** v1.5

В тестовых и реальных задачах ассистент может в любой момент **спросить совета**:

```
Ассистент: «Бот, я застрял на ТЗ #2 — не понимаю как искать
            лицензии в репозиториях, есть подсказка?»

Бот: «По методике проекта ты должен искать в файле LICENSE
      в корне репо или в правой панели GitHub.
      Не подсказываю решение — только методику.
      Если совсем тупик — поставь задачу на паузу
      и попроси модератора уточнить.»
```

**Почему важно:** Главное что в задачах оценивается — **умение работать с ИИ**. Дать ассистенту своего ИИ-наставника — естественно для платформы.

**Граница:** наставник помогает с методикой, не выдаёт решения. Это часть оценки.

**Реализация:** Sonnet 4.6 с system-промптом «ты methodology coach, не solution provider». Промпт + интеграция в бот.

---

### 5. Предотвращение выгорания

**Импакт:** средний | **Сложность:** низкая | **Когда:** v1.5

Система видит сигналы перегруза и сама вмешивается:

- Ассистент за день взял 4+ задач подряд → бот тактично спрашивает «Сделай паузу?»
- Качество падает (3 задачи с замечаниями подряд) → пауза + предложение разобрать «что не так»
- Не было дня отдыха за 7 дней → напоминание «возьми выходной»
- Резкий рост ставки → проверка устойчивости (не «один удачный день»)

**Почему важно:** Документы оптимизированы под «выжать максимум». Это даёт быстрое сгорание. Системная забота держит людей дольше.

**Реализация:** cron-job смотрит метрики, отправляет тактичные нотификации.

---

### 6. Match-making заказчик ↔ ассистент

**Импакт:** высокий | **Сложность:** высокая | **Когда:** v2

Когда новая задача появилась — система не выбирает по примитивному round-robin или «лучший рейтинг». Она учит на истории:

- Какие ассистенты лучше работают с задачами **этого** заказчика
- Какие типы задач у каждого ассистента идут лучше
- Время суток когда конкретный человек продуктивнее
- Связки «исполнитель + ревьюер» — некоторые пары работают слаженнее

Через 2-3 месяца использования система знает команду лучше чем менеджер.

**Почему важно:** Это и есть «замена менеджера» по-настоящему. Не «нажми кнопку вместо меня», а «принимай лучшие решения чем я».

**Реализация:** простое embedding + retrieval по истории. На малых объёмах (до 100 задач) не нужно ML — статистика + правила.

---

### 7. Карьерный трек ассистент → специалист → управленец

**Импакт:** высокий | **Сложность:** средняя | **Когда:** v2

В презентации Дмитрия упомянуто:
> «По мере работы вы можете вырасти в специалиста или управленца»

Но **в документах не сказано как**. Это размытое обещание.

Платформа делает рост измеримым:
- ✅ 50 задач принято полностью → можешь претендовать на роль специалиста по направлению X
- ✅ Помог 5 другим ассистентам в спорах как судья → можешь быть постоянным судьёй
- ✅ 6 месяцев стабильно >290₽/час + ввёл 3 идеи в работу → готов вырасти в управленца

Прозрачные критерии → люди реально растут, а не уходят через 3 месяца.

**Реализация:** правила в БД + dashboard «твой карьерный путь».

## 🎁 Дополнительные идеи (бонус)

### 8. Открытое портфолио (с согласия заказчика)

Ассистент может «закрепить» хорошо выполненную задачу в публичное портфолио. При найме новых ассистентов или PR проекта — это готовый набор кейсов.

### 9. Парные задачи (для обучения)

Новичка можно посадить «парой» к опытному ассистенту. Опытный делает, новичок наблюдает (или наоборот). Оплачивается обоим, опытный получает бонус за наставничество.

### 10. Внутренний рынок переуступки задач

Ассистент взял задачу но не успевает. Может **переуступить** другому ассистенту через бота. Оба получают долю оплаты по договорённости. Платформа берёт небольшую комиссию.

### 11. Анти-фрод детектор

ИИ смотрит на паттерны:
- Подозрительно похожие решения у разных кандидатов
- Время выполнения сильно ниже среднего
- Одинаковые промпты в описаниях работы с ИИ

Не блокирует — но помечает для коммуникатора.

### 12. Голосовой ввод отчётов

Ассистент после задачи говорит голосом 1-2 минуты «что сделал, как работал с ИИ, что было сложно». Whisper → текст → структурированный отчёт. Экономит время + чаще честно.

### 13. Calendar-интеграция

Согласованное окно работы автоматически попадает в Google Calendar ассистента (опционально). Меньше пропусков, больше структуры.

### 14. Multi-tenant с самого начала

Архитектура с поддержкой нескольких «команд» (tenants) с первого дня. Тогда продать как SaaS другим компаниям — не переписывание, а конфигурация.

### 15. Публичный лидерборд (анонимный)

Топ-10 ассистентов недели без имён, только аватары и метрики. Здоровая конкуренция + социальное доказательство для новичков.

## 🚨 Что в текущей концепции потенциально слабо

### A. «Реакция в общем чате» из документов

Уже разобрали — переходим на адресную рассылку с кнопками. ✅ Учтено в концепции.

### B. Подготовка 4 документов на каждую задачу

В документах — обязательно для **каждой** задачи. Это **большая нагрузка** на ассистента: помимо самой задачи нужно ещё 4 документа создать.

**Предложение:** автоматизировать через бота. Ассистент пишет только результат + список умышленных ошибок. Бот сам форматирует в 4 документа по шаблонам.

### C. Отсутствие «light» режима задач

Все задачи проходят полный ревью-цикл. Но мелкая задача на 15 минут с ревью на 30 минут — экономически бессмысленно.

**Предложение:** ввести «light» статус для задач <30 минут — ревью необязательно, ассистент несёт полную ответственность.

### D. Жёсткая бинарность «принято / не принято»

В реальности есть «принято на 80%». Текущая шкала режет хорошие работы в «не принято» из-за мелочей.

**Предложение:** градации (принято / принято с замечаниями / принято с правками / не принято). Уже намечено в документах через «не принята» vs «с замечаниями», но не строго.

### E. Нет упоминания обучения

В презентации Дмитрия: «Обучение бесплатное если не сложилось». Но **в системе нет встроенного механизма обучения**. Получается обучение = внешний процесс.

**Предложение:** мини-уроки внутри бота. После каждой «не принятой» задачи бот предлагает 5-минутный материал по слабому месту.

### F. Никакой работы с заказчиком

Платформа не помогает заказчику оформить хороший ТЗ. Если он напишет плохое ТЗ — у ассистента не будет шансов.

**Предложение:** ИИ-помощник для заказчика. Заказчик описывает задачу в свободной форме — бот предлагает критерий приёмки, лимит, дедлайн. Если критерия нет — нельзя отправить в очередь.

### G. Нет «backup исполнителя»

Если ассистент взял задачу и пропал — задача висит. Нужен механизм автоматической передачи.

**Предложение:** если не было апдейтов 4+ часа и не на паузе — система автоматически возвращает задачу в очередь и шлёт следующему.

## 🔧 Технические улучшения

### T1. Backup стратегия с первого дня

Neon делает point-in-time recovery только на платных планах. На free tier — снэпшоты по расписанию. Настроить backup до первого реального кандидата.

### T2. Audit log всех решений

Каждое решение системы (ИИ или детерминированное) пишется в `audit_log` с входными данными и обоснованием. Можно «доказать» почему конкретного кандидата приняли/отказали — для прозрачности и для отладки ИИ.

### T3. Версионирование промптов оценщика

Промпты ИИ-оценщика хранить в БД с версиями, не в коде. Тогда можно безопасно править формулу оценки без деплоя.

### T4. Telegram Mini App (вместо команд) для дашборда

В долгосрочке — `/stats` команды устаревают. Telegram Mini App = React-приложение прямо внутри Telegram. Это будущее, но архитектурно учесть.

### T5. Webhook от GitHub / Linear / Jira для входящих задач

Если заказчики ставят задачи в Linear/Jira — webhook автоматически создаёт задачу в нашей платформе. Не нужно дублировать ввод.

## 📋 Что взять в MVP — short-list

Из всего списка выше — **в MVP стоит**:

1. ✅ **Self-service кабинет** (#1) — низкая сложность, высокий импакт на удержание
2. ✅ **Прогресс-бар до повышения** (#2) — почти даром, мощный психологический эффект
3. ✅ **Карточка кандидата для коммуникатора** (#3) — реально экономит время
4. ✅ **ИИ-помощник для заказчика** (#F) — без хороших ТЗ всё ломается
5. ✅ **Backup и audit log** (#T1, #T2) — критическая гигиена

Остальные — в v1.5 и v2 после первых реальных кандидатов и обратной связи.

## Что обсудить с Дмитрием

- Какие из этих улучшений резонируют с его видением
- Что он считает «лишним» (мы можем потерять фокус)
- Есть ли у него свои идеи которые мы не учли
- Готов ли он к тому что платформа «думает» — то есть предлагает повышения, замечает выгорание, выбирает ассистента

Список этих улучшений можно показать как **отдельный слайд** в презентации — называется «Что мы предлагаем сверх документов».
