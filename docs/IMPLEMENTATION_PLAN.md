# План реализации Assistant Hub

> **Подход:** MVP = качественная платформа с peer-review, грейдами, типизацией ошибок и правилами оплаты с первого дня. ИИ-обвес и полная взаимопроверка — поэтапные доработки с явными триггерами запуска.
>
> **Все цифры — точные, без диапазонов. Максимум 8ч на фазу.**

---

## Общая структура

```
MVP                            71 час        ~1.5-2 недели вдвоём
   └─ полностью работающая платформа с peer-review и грейдами

ДОРАБОТКА I                    32 часа       по триггерам
   └─ ИИ-агенты, личный кабинет, шаблоны, авто-пересмотр ставки

РАЗВИТИЕ II                    60 часов      по триггерам
   └─ полная взаимопроверка, Manager Hub, multi-brain, прод-VPS
```

**Итого до полной системы:** 163 часа, растянуто на 3–4 месяца постепенно.

**Команда разработки:** Коля + Евгений работают парой с взаимным ревью по этапам. Согласование с менеджерами (Дмитрий, Александр) — батчем, один раз на этап.

---

# MVP (71 час)

**Цель:** Полноценная платформа с онбордингом, реальными задачами, peer-review и грейдами. Без ИИ-обвеса (это Доработка I), без полной взаимопроверки с 4 документами (это Развитие II). Но с правильным ПДн-flow, ACL, напоминаниями, типизацией ошибок, грейдами и автоматизацией возвратов.

## Фаза M5: Тестовое задание + напоминания — 6ч

| Задача | Критерий приёмки |
|--------|-----------------|

## Фаза M6: Дашборд оценки + ACL + типизация ошибок — 8ч

| Задача | Критерий приёмки |
|--------|-----------------|
| Полноценный ACL через таблицу `operators` | Команды модератора недоступны кандидатам. Декоратор `@require_role` |
| Команда `/queue` со списком сданных | Карточки: имя/направление/балл/ссылка/время сдачи. Фильтр по статусу |
| Кнопки решения «принять / на созвон / отказ» | Меняет статус кандидата, шлёт уведомление |
| Поле для комментария модератора | После решения — может ввести комментарий, идёт в уведомление кандидату |
| Типизация ошибок при отклонении/возврате | 4 типа кнопок: format / incomplete / mismatch_tz / critical (читаются из `error_types`). Сохраняется в `reviewer_decision` |

|--------|-----------------|

## Фаза M9: Сценарии поведения для код-задач — 2ч

| Задача | Критерий приёмки |
|--------|-----------------|
| При `/done` для задач `type=code` требуется behavior_scenarios | Формат `«X → Y»`, минимум 1 пункт |
| Валидация формата | Без сценариев `/done` отклоняется с пояснением |
| Сохранение в `task_assignments.behavior_scenarios` | Доступно проверяющему B в M12 и менеджерам |

## Фаза M10: Распределение (гибрид тендер→round-robin) + учёт времени — 6ч

| Задача | Критерий приёмки |
|--------|-----------------|
| Публикация задачи в общий канал на N минут | N из `config.tender_window_minutes` (5–10). Inline-кнопка «Взять» |
| Первый кто нажал — забирает | Atomic update task_assignments. Остальным — «уже взяли» |
| Если за окно никто не взял — fallback round-robin | Первый свободный активный ассистент. Не сам автор задачи. Если все заняты — в очередь |
| Адресная рассылка с кнопками «Принять/Отказ» + таймаут | Если не ответил за N мин — переход к следующему |
| Учёт фактического времени (start/pause/end) | Команды `/start_work`, `/pause`, `/done`. actual_hours в БД (только для аналитики) |

---

## Фаза M11: Оплата + апелляция + возвраты + не-сдачи — 7ч

| Задача | Критерий приёмки |
|--------|-----------------|
| Оплата = `time_limit × rate_по_грейду` | Сумма фиксируется в `task_assignments.payout` при `/accept` |
| Апелляция лимита 1 раз до `/start_work` | Кнопка «Запросить пересмотр лимита» с полем обоснования. Модератор решает |
| Правила возвратов из `retry_policies` | 1-я: ×1.0, 2-я: ×0.8, 3-я: transfer другому исполнителю |
| Сброс счётчика `tasks_clean_count` при `mismatch_tz`/`critical` | `assistants.tasks_clean_count = 0` |
| Правило «не сдал в срок» | После deadline + `config.deadline_grace_minutes` → автовозврат в очередь, payout = 0, audit_log |
| Счётчик `failed_deadlines_this_month` | При значении из `config.failed_deadline_pause_threshold` (3) — `paused_until` = +1 неделя, уведомление модератору |

## Фаза M12: Peer-review lite — 8ч

| Задача | Критерий приёмки |
|--------|-----------------|
| Выбор B после `/done` ассистента A | Не A, не на паузе, не overloaded. Если нет свободных — ждёт |
| Уведомление B с задачей + результатом + чек-листом | Чек-лист 5–7 пунктов из `config.peer_review_checklist` |
| Кнопки «ОК» / «Есть замечания» | При «замечания» — выбор типа ошибки из 4 типов |
| При «ОК» — пакет идёт менеджерам | Дмитрий/Александр получают уведомление с полным контекстом (результат + сценарии + проверка B) |
| При «замечания» — возврат A | Применяются правила из `retry_policies`. retry_count++ |
| Оплата B за проверку | 50 ₽ из `config.peer_review_pay_rub`. Начисляется при любом решении |
| Audit log всех действий B | Полный аудит для прозрачности |

## Что MVP даёт

- Корректный onboarding с согласием на ПДн (152-ФЗ)
- FSM с реактивацией прерванной анкеты
- Отборочное тестовое с мягкими напоминаниями 24/48/72ч
- Полноценный ACL ролей (модератор, ассистент, кандидат)
- Дашборд оценки + типизация ошибок (4 типа)
- Создание реальных задач с полной карточкой
- Pre-start план + сценарии поведения для код-задач

- Оплата по лимиту + апелляция + правила возвратов
- Автоматическая обработка «не сдал в срок»
- Грейды Junior/Middle/Senior (ручное переключение менеджером)
- Peer-review lite перед отправкой к менеджерам
- Сводка для выплат в понедельник
- Audit log всех решений
- Все правила в Neon — готовы к подключению ИИ-агентов

# Главные риски

| Риск | Митигация |
|------|-----------|
| Промпт-инженерия в D1 | Запас 8ч на ИИ-оценщик, тестируем на накопленных за MVP реальных тестах |
| Материалы менеджеров задерживаются | M1–M5 не зависят от их материалов, можно стартовать сразу |
| Peer-review создаст лишний оверхед на старте | Окно тендера 5–10 мин подкручиваем; если все ассистенты busy — B выбирается из Коли/Евгения как фоллбек |
| Грейды покажут неправильные пороги | Числа в Neon, корректируем через `UPDATE config SET value = ...` без деплоя |

# Процесс согласования и работы

1. Коля + Евгений вместе разбивают фазу M? на конкретные задачи.
2. Делают, взаимно ревьюят друг друга.
3. По завершении фазы — отчёт в общий чат с Дмитрием и Александром (батчем).
4. Менеджеры дают добро или возвращают на доработку.
5. Старт следующей фазы.

Перед каждой фазой — карточка в общем чате с целью / критериями / лимитом. Можно пакетом 2–3 фазы.
