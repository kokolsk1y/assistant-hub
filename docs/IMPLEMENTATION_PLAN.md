# План реализации Assistant Hub

Структурированный план разработки в формате методики Дмитрия:
**каждая задача = цель + критерий приёмки + лимит времени + дедлайн**.

---

## Контекст планирования

- **Старт:** после созвона с Дмитрием (согласование концепции)
- **Темп:**
  - Неделя 1 — интенсивная работа (6-8ч/день, ~50ч)
  - Недели 2-3 — вечерами (3-4ч/день, ~25-35ч/неделя)
- **Итого:** 100-130 часов на MVP
- **Параллельно:** Коля сдаёт экзамены — планируем с запасом
- **Темп согласования:** каждая задача согласуется с Колей перед началом (GSD interactive mode)

## Детальный план — задачи в формате методики

### 🟢 Фаза 0: Подготовка инфраструктуры

#### Задача 0.1 — Установка WSL2 + Node 24 + OpenClaw

**Цель:** OpenClaw запущен и доступен через `openclaw gateway status` в WSL2 Ubuntu.

**Критерий приёмки:** Количество запущенных компонентов из списка (5):
1. WSL2 Ubuntu 22.04+ установлен
2. Node.js 24 через nvm
3. OpenClaw 2026.5.18+ установлен глобально
4. `openclaw gateway status` показывает "running"
5. Web dashboard открывается на http://localhost:18789

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 1, до 12:00

#### Задача 0.2 — Создание Neon базы и TG-ботов

**Цель:** Получены все необходимые credentials для разработки.

**Критерий приёмки:** Количество элементов в `.env.local` (5 обязательных):
- `DATABASE_POOLED_URL` (Neon, новая база `assistant_hub_dev`)
- `DATABASE_DIRECT_URL` (для миграций)
- `TG_BOT_TOKEN_DEV` (dev-бот через @BotFather)
- `TG_BOT_TOKEN_PROD` (prod-бот, на потом)
- `OPENROUTER_API_KEY` (свой или от Дмитрия)

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 1, до 16:00

#### Задача 0.3 — Инициализация Python-проекта

**Цель:** Структура проекта готова к разработке.

**Критерий приёмки:** Количество созданных файлов (минимум 5):
- `pyproject.toml` с зависимостями (aiogram, asyncpg, openai, pydantic, apscheduler)
- `src/bot/main.py` (заглушка с polling)
- `src/db/schema.sql` (пока пустой)
- `src/config.py` (загрузка из .env)
- `.env.example`

**Лимит:** 1.5 часа
**Дедлайн:** Неделя 1, день 1, до 18:00

**Цель:** Бот отвечает на `/start`.

**Критерий приёмки:** При отправке `/start` в dev-боте — ответ приходит за <2 сек, в логах виден chat_id и текст.

**Лимит:** 2 часа

#### Задача 1.2 — Connection к Neon Postgres

**Цель:** Бот может читать и писать в Neon.

**Критерий приёмки:** Команда `/dbtest` пишет в таблицу `debug_log` запись и возвращает её содержимое. Время операции < 500мс.

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 2, до 16:00

### 🟢 Фаза 2: Схема БД + FSM-каркас

#### Задача 2.1 — Создать миграции базы (5 таблиц)

**Цель:** В Neon созданы основные таблицы.

**Критерий приёмки:** Количество созданных таблиц (5):
- `candidates` (FSM-state + анкета)
- `tests` (библиотека тестовых заданий)
- `test_submissions` (сданные результаты)
- `tasks` (реальные задачи от заказчиков)
- `audit_log` (история всех решений)

Все имеют первичный ключ, индексы, timestamps.

**Лимит:** 2.5 часа
**Дедлайн:** Неделя 1, день 2, до 22:00

#### Задача 2.2 — Реализация FSM через asyncpg

**Цель:** Состояние пользователя сохраняется в БД, переживает рестарт бота.

**Критерий приёмки:** Тест: запустить бота → начать `/start` → выключить бота → включить → состояние восстановлено корректно. Без потерь.

**Лимит:** 3 часа
**Дедлайн:** Неделя 1, день 3, до 13:00

#### Задача 2.3 — Согласие на ПДн (ФЗ-152)

**Цель:** Первое сообщение бота — запрос согласия с кнопкой.

**Критерий приёмки:** Количество корректных переходов:
- Согласие → переход к анкете
- Отказ → вежливое прощание
- Согласие сохранено с timestamp в БД
- Без согласия команда `/start` не идёт дальше

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 3, до 17:00

#### Задача 2.4 — Глобальные команды (/cancel, /me, /help)

**Цель:** Базовые команды работают в любом состоянии FSM.

**Критерий приёмки:** Количество работающих команд (3) + правильное поведение `/cancel` (сбрасывает state не теряя данные).

**Лимит:** 1.5 часа
**Дедлайн:** Неделя 1, день 3, до 20:00

### 🟢 Фаза 3: Анкета новичка

#### Задача 3.1 — 4 вопроса с inline keyboards

**Цель:** Кандидат проходит анкету за <2 минуты.

**Критерий приёмки:** End-to-end тест: новый пользователь → /start → согласие → 4 ответа через кнопки → состояние "анкета пройдена". Время < 2 мин.

**Лимит:** 3 часа
**Дедлайн:** Неделя 1, день 4, до 13:00

#### Задача 3.2 — Сохранение источника (UTM-метка)

**Цель:** Бот корректно парсит `?start=src_X` и сохраняет источник.

**Критерий приёмки:** 5 разных deeplink-ов (src_presentation_v1, src_tg_itfree, etc) → каждый сохраняется в `candidates.source` корректно.

**Лимит:** 1.5 часа
**Дедлайн:** Неделя 1, день 4, до 16:00

#### Задача 3.3 — Реактивация прерванной анкеты

**Цель:** Если кандидат бросил на 2-м вопросе — может продолжить через сутки.

**Критерий приёмки:** Тест: пройти 2 вопроса → закрыть → через 1 час повторить /start → бот предлагает «продолжить с того места» и/или начать заново.

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 4, до 19:00

### 🟢 Фаза 4: Библиотека тестов + выдача

#### Задача 4.1 — Заполнить таблицу tests из библиотеки

**Цель:** В БД лежат тестовые задания.

**Критерий приёмки:** Количество записей в таблице tests (минимум 6: 1 отборочное + 5 стартовых из документов Дмитрия). Каждая запись содержит: title, text, direction, level, expected_time_minutes, criteria.

**Лимит:** 2 часа (если используем тексты Дмитрия как есть; если переписываем — +3 часа отдельной задачей)
**Дедлайн:** Неделя 1, день 4, до 22:00

#### Задача 4.2 — Алгоритм подбора задачи под профиль

**Цель:** По направлению + уровню система выдаёт подходящую задачу.

**Критерий приёмки:** 4 разных профиля кандидата → 4 разных подобранных задачи (без коллизий). Если профиль не покрыт — fallback на универсальную.

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 5, до 13:00

#### Задача 4.3 — Выдача задачи с таймером

**Цель:** Бот выдаёт задание и запускает таймер с напоминаниями.

**Критерий приёмки:** После выдачи задачи → APScheduler планирует 3 напоминания (через 24ч / 48ч / 72ч). Тест: ускорить таймер до 30 сек/30 сек/30 сек → получить 3 сообщения.

**Лимит:** 3 часа
**Дедлайн:** Неделя 1, день 5, до 18:00

### 🟢 Фаза 5: Приём результата + базовый дашборд

#### Задача 5.1 — Приём текста / файла / ссылки от ассистента

**Цель:** Ассистент может сдать результат любого типа.

**Критерий приёмки:** 3 типа сдачи проходят успешно: текст, файл (.pdf/.docx), URL. Все сохраняются в `test_submissions`.

**Лимит:** 2.5 часа
**Дедлайн:** Неделя 1, день 6, до 13:00

#### Задача 5.2 — Очередь "на оценку" для модератора (Дмитрия)

**Цель:** У модератора есть команда `/queue` показывающая ожидающие оценки сдачи.

**Критерий приёмки:** Команда работает только для модератора (ACL). Возвращает список с inline keyboards «принято / на созвон / отказ» по каждой.

**Лимит:** 3 часа
**Дедлайн:** Неделя 1, день 6, до 19:00

#### Задача 5.3 — Запись решения в БД + уведомление кандидату

**Цель:** При нажатии модератором «принято» — кандидат получает уведомление, статус меняется в БД.

**Критерий приёмки:** Все 3 решения (принято / созвон / отказ) корректно изменяют статус кандидата и шлют соответствующее сообщение.

**Лимит:** 2 часа
**Дедлайн:** Неделя 1, день 7, до 13:00

### 🟡 Фаза 6: ИИ-оценщик тестов

#### Задача 6.1 — Интеграция OpenRouter с фоллбеком

**Цель:** Базовый ИИ-вызов работает с явным `max_tokens` и retry.

**Критерий приёмки:** Тестовый вызов Sonnet 4.6 → JSON ответ → парсинг через Pydantic. Симулированный отказ (429) → корректный fallback на «ручная оценка». Тест 3 раза подряд успешно.

**Лимит:** 3 часа
**Дедлайн:** Неделя 2, день 1, вечер

#### Задача 6.2 — System-промпт оценщика по рубрике критериев

**Цель:** Промпт даёт стабильную оценку по 5 критериям рубрики.

**Критерий приёмки:** 3 разных тестовых ответа кандидата → 3 оценки. Запуск каждой дважды → разброс баллов не более 10/100. Каждый ответ — валидный JSON по Pydantic-схеме.

**Лимит:** 4 часа (промпт-инженерия — самое сложное)
**Дедлайн:** Неделя 2, день 2, вечер

#### Задача 6.3 — Decision logic (детерминированная)

**Цель:** Балл → решение по правилам (не ИИ).

**Критерий приёмки:** Тест на 6 граничных случаях (балл 100, 71, 70, 45, 44, 0) → корректные решения (approved/borderline/rejected). ИИ только если score 30-70 — на спорные привлекаем Opus.

**Лимит:** 2 часа
**Дедлайн:** Неделя 2, день 3, утро

#### Задача 6.4 — Audit log решений

**Цель:** Каждое решение ИИ записано с входными данными и обоснованием.

**Критерий приёмки:** После 10 оценок в `audit_log` 10 записей с: input_data, prompt_version, model_used, output_json, decision, timestamp.

**Лимит:** 1.5 часа
**Дедлайн:** Неделя 2, день 3, утро

**Лимит:** 2 часа
**Дедлайн:** Неделя 2, день 3, вечер

### ⭐ Фаза 7.5: Manager Hub бот (proxy-коммуникации)

> Новая фаза. Реализация ключевой архитектурной идеи: все коммуникации управленцев с ассистентами идут через отдельного бота, не через личку.

#### Задача 7.5.1 — Второй TG-бот «Manager Hub»

**Цель:** Отдельный бот для управленцев работает.

**Критерий приёмки:** При запуске Manager Hub бота → команда `/start` доступна только для пользователей с ролью `manager` или `communicator` в БД. Остальные получают «нет доступа».

**Лимит:** 2 часа
**Дедлайн:** Неделя 2, день 3, вечер

#### Задача 7.5.2 — Главное меню Manager Hub

**Цель:** Управленец видит реактивное меню действий.

**Критерий приёмки:** Inline keyboard с разделами:
- 👥 Команда (список ассистентов + рейтинг)
- 📋 Задачи (открытые / в работе / на ревью)
- 📞 Очередь на созвон (кандидаты в статусе borderline)
- 📊 Метрики недели
- ➕ Создать задачу
- 📨 Шаблоны рассылок

**Лимит:** 3 часа
**Дедлайн:** Неделя 2, день 4, утро

#### Задача 7.5.3 — Карточка ассистента с действиями

**Цель:** Управленец может посмотреть карточку любого ассистента и совершить действие.

**Критерий приёмки:** Карточка содержит: контакт, текущий рейтинг, ставку, последние 5 задач, метрики. Inline-кнопки: «📞 Назначить созвон», «💬 Написать», «⏸ Поставить на паузу», «📈 Изменить ставку».

**Лимит:** 4 часа
**Дедлайн:** Неделя 2, день 4, вечер

#### Задача 7.5.4 — Proxy-сообщения через шаблоны

**Цель:** Управленец пишет в Manager Hub → ассистенту приходит красивое сообщение в его боте.

**Критерий приёмки:** 4 шаблона работают:
- «Назначить созвон» (с датой/временем/ссылкой + кнопка «Подтвердить»)
- «Замечание по работе» (с указанием задачи)
- «Благодарность» (просто текст)
- «Объявление команде» (рассылка всем активным)

Все коммуникации логируются в `messages` таблицу.

**Лимит:** 4 часа
**Дедлайн:** Неделя 2, день 5, утро

#### Задача 7.5.5 — Audit log всех proxy-коммуникаций

**Цель:** Каждое сообщение через платформу — в БД с метаданными.

**Критерий приёмки:** Таблица `messages` содержит: from_user_id, to_user_id, template_used, content, sent_at, delivered_at, read_at. Тест: 10 сообщений → 10 записей с правильными данными.

**Лимит:** 2 часа
**Дедлайн:** Неделя 2, день 5, утро

### 🟡 Фаза 8: Реальные задачи + распределение кнопками

#### Задача 8.1 — Таблица tasks + flow создания задачи

**Цель:** Модератор может создать задачу через `/newtask`.

**Критерий приёмки:** Команда работает только для модератора. Спрашивает: текст, критерий приёмки, лимит, дедлайн. Сохраняет в БД со статусом "open".

**Лимит:** 3 часа
**Дедлайн:** Неделя 2, день 4, вечер

#### Задача 8.2 — Алгоритм выбора ассистента (round-robin)

**Цель:** При создании задачи система выбирает первого ассистента.

**Критерий приёмки:** 5 задач подряд → 5 разных ассистентов (среди 5+ свободных). Учёт текущей загрузки (у занятого не берёт).

**Лимит:** 2 часа
**Дедлайн:** Неделя 2, день 5, утро

#### Задача 8.3 — Адресная рассылка с кнопками «Принять / Отказ»

**Цель:** Выбранный ассистент получает сообщение в личке с кнопками.

**Критерий приёмки:** Тест: задача создана → ассистент получил → нажал «Принять» → статус задачи "in_progress", таймер запущен, у других не висит.

**Лимит:** 3 часа
**Дедлайн:** Неделя 2, день 5, вечер

#### Задача 8.4 — Таймаут ответа + переход к следующему

**Цель:** Если ассистент не ответил за N минут — задача уходит следующему.

**Критерий приёмки:** Конфигурируемый таймаут (по умолчанию 10 мин). Тест: симулировать пропуск → задача перешла дальше. Логи фиксируют отказ.

**Лимит:** 2 часа
**Дедлайн:** Неделя 2, день 6, утро

#### Задача 8.5 — Учёт фактического времени (start / pause / end)

**Цель:** Часы считаются корректно с учётом пауз.

**Критерий приёмки:** Тест-сценарий: задача началась 14:00 → пауза 14:30 → возобновлена 15:00 → завершена 16:30. Учтено 2ч (не 2.5ч). Дедлайн сдвинут на 30 мин.

**Лимит:** 3 часа
**Дедлайн:** Неделя 2, день 6, вечер

#### Задача 8.6 — Напоминания о дедлайне через APScheduler

**Цель:** За 4ч / 1ч до дедлайна — напоминание.

## ⚠️ Риски и буферы

| Риск | Вероятность | Митигация |
|------|-------------|-----------|
| OpenClaw не запускается на Windows | Средняя | Запасной план: прямые вызовы OpenRouter из Python. Фаза 1 имеет 3ч буфер на задачу 1.3 |
| Промпт-инженерия оценщика занимает >4ч | Высокая | Фаза 6 — самая рискованная. Заложили 14ч (среднее 4ч на задачу). Если буксуем — упрощаем рубрику |
| Дмитрий не успевает дать ответы / материалы | Средняя | Фазы 1-5 не зависят от его ответов. Если нужны материалы (например финальные тесты) — используем черновики из документов |
| Экзамены Коли задерживают темп | Высокая (по факту) | Неделя 1 интенсив = до экзаменов. Недели 2-3 вечером = совмещение. Если экзамены давят — переносим Фазу 12 на потом |
| Сложности с ревью (Фаза 9 — 14-20ч) | Высокая | Самая большая фаза. Если буксуем — выпускаем MVP без ревью, оно идёт v1.1 |
