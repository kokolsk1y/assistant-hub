# Assistant Hub

## What It Is

Платформа-координатор, которая постепенно заменяет ручную работу менеджеров (Дмитрий, Александр) по сопровождению команды ассистентов-вайбкодеров. Покрывает путь от первого отклика на HR-воронку до завершения оплачиваемой задачи. Точка входа для пользователей — Telegram. Мозги — OpenClaw + multi-agent OpenRouter. Память и правила — Neon Postgres. Со временем — SaaS.

## The Problem

Сейчас менеджеры вручную делают:

- Фильтруют отклики из HR-воронки (TG-паблики + hh.ru)
- Скидывают кандидату презентацию и ждут реакции
- Выдают тестовое задание под направление
- Лично оценивают результат
- Помнят кто что умеет, кто свободен, кто на каком уровне
- Считают часы по каждому ассистенту, ставят дедлайны
- Принимают работу, сверяются с ТЗ, разбираются с косяками
- Координируют выплаты

С ростом команды это упирается в людей-узких мест. Кандидаты теряются, дедлайны забываются, нет единой памяти про ассистентов, ИИ-агенты без структурированной памяти галлюцинируют. **Без системы рост невозможен.**

## Target Users

- **Новичок (кандидат)** — пришёл из hh.ru или TG-паблика по отклику. Знает мало, ждёт быстрый ответ и понятный процесс. Уйдёт если онбординг кривой.
- **Подтверждённый ассистент** — уже прошёл онбординг. Берёт реальные задачи, отчитывается, проверяет работу других. Хочет: чёткое ТЗ, прозрачная оплата по грейдам (Junior 200 ₽/ч → Middle 250 → Senior 300), рост.
- **Менеджеры (Дмитрий, Александр)** — заказчики, выдают задачи и принимают отчётность. В операционке не сидят. Хотят: меньше ручной работы, не упускать кандидатов, видеть кто свободен/хорош, получать данные для выплат. Выплаты делают **сами** — мы только агрегируем. Зона менеджеров также: общение с заказчиками и приём заказов.
- **Команда разработки (Коля + Евгений)** — пара на равных, строят план и задачи вместе, взаимно ревьюят, согласуют батчем с менеджерами.
- **Коммуникатор (Евгений в роли коммуникатора)** — проводит созвоны с новичками, мотивирует, разруливает спорные ситуации. Получает уведомления от бота в личку TG когда нужно действовать.

## Success Criteria (v1)

v1 = **полный онбординг-пайплайн + работа с реальными задачами с peer-review** (расширили после ревью Евгения, см. `REVIEW_RESPONSE.md`).

- Новичок попадает в TG-бот по QR/ссылке из презентации
- Проходит короткую анкету (направление, уровень, опыт с ИИ)
- Получает тестовое задание из **нашей собственной библиотеки**, под направление и уровень
- Сдаёт результат в бота
- ИИ-агент **не** оценивает в MVP — модератор сам нажимает кнопки решения (с типизацией ошибок, см. ниже). ИИ-оценщик — фаза D1.
- **Мягкий дедлайн на сдачу тестового**: после выдачи задания запускаются напоминания — через 24ч / 48ч / 72ч. После 72ч кандидат помечается как «отвалился» (НЕ финальный отказ), его можно реактивировать.
- Решение «годен / спорный → созвон / отказ» — **рекомендация для модератора**, не финальный отказ (по ТК РФ ст. 86 нельзя автоматически отказывать на основании только автоматизированной обработки).
- Все данные новичка + балл + история сохраняются в Neon. **Реквизиты карты — НЕ собираем в v1.** Сбор реквизитов = отдельный флоу v2 при первой ЗП.
- Коммуникатор получает в личку TG сводку по новичкам которым нужен созвон.
- Менеджеры получают дайджест прошедших тест (контакт + балл + анкета, БЕЗ финансов).
- **Принятый ассистент** получает реальные задачи через гибрид-распределение: задача публикуется в общий канал на 5–10 мин (тендер), потом fallback на round-robin.
- **Полная карточка задачи** с обязательными полями: `expected_result`, `context_materials`.
- **Pre-start план** ассистента перед `/start_work`.
- **Сценарии поведения «X → Y»** обязательны при сдаче код-задач.
- **Оплата по лимиту** задачи × ставка грейда. Факт-часы для аналитики.
- **Peer-review lite** перед отправкой к менеджерам.
- **Дашборд для контроля и аналитики (через TG-команды):** менеджеры могут запросить у бота сводку — кто на каком этапе воронки, сколько новичков прошло/отвалилось за период, фильтры по направлениям/уровням. В v1 — онбординг + базовая работа с задачами. В v2 расширим. Веб-дашборд — v3.

## Hard Constraints

- **Стек: OpenClaw (с Доработки I) + Neon Postgres + OpenRouter + Telegram Bot API.** Без n8n (платный). Без своих ML-моделей.
- **OpenClaw НЕ запускался ранее на этом ПК** — операционный риск, отдельная фаза при подключении ИИ.
- **Хостинг: локально на ПК Коли** на этапе MVP. Продакшн → отдельная фаза, через VPS.
- **Язык интерфейса — только русский.** Все сообщения бота, тестовые задания, отчёты, дашборды.
- **Multi-brain архитектура**: каждый ИИ-агент решает узкую задачу и отчитывается другому в строгом JSON-формате со схемой. Цель — избежать галлюцинаций и кросс-агентных ошибок коммуникации.
- **Скелет сначала, ИИ потом.** Deterministic-логика (БД, состояния FSM, обработка команд, маршрутизация в TG) должна работать без ИИ. ИИ — слой улучшения поверх работающего скелета.
- **Правила бизнес-логики живут в Neon с первого дня.** Грейды, типы ошибок, коэффициенты доработки, окно тендера, grace-периоды, чек-листы peer-review, триггеры фаз — всё в таблицах БД, **не в коде и не в env**. Чтобы детерминированный код и ИИ-агенты (D1, D4, R1, R3) читали правила из одного источника без рассинхрона. Изменение правила = `UPDATE` в БД без рестарта бота.
- **Модели OpenRouter — хорошие** (Claude Sonnet 4.6 / Opus 4.7 для оценки и сложных решений; Haiku 4.5 — для маршрутизации/коротких задач ради бюджета). Окончательный выбор — после пробных прогонов.
- **Не лезем в выплаты, налоги, чеки, приём заказов.** Это всё — зона менеджеров.
- **Декомпозиция задач разработки: максимум 8 часов на фазу.** Каждая фаза самостоятельная.
- **Команда разработки:** Коля + Евгений, работают парой с взаимным ревью по этапам.
- **Согласование с менеджерами — батчем**, один раз на этап, через общий чат с Дмитрием и Александром. Не дёргаем их по мелочам.

## Бизнес-правила (хранятся в Neon, описаны здесь для команды)

### Грейды ассистентов

| Грейд | Ставка | Условия перехода |
|-------|--------|------------------|
| **Junior** | 200 ₽/ч | Стартовая для всех новых |
| **Middle** | 250 ₽/ч | 10 принятых задач без возврата `mismatch_tz`/`critical` **И** ≥2 недели в команде |
| **Senior** | 300 ₽/ч | 30 задач всего **И** ≥1 месяц в Middle |

**Кто меняет грейд в MVP:** Дмитрий/Александр руками раз в неделю смотрят сводку (`/grade_review`) и применяют через `/set_grade @user middle`. После запуска D4 — автоматически. Структура таблицы `grades` в Neon готова к подключению D4.

**Сброс счётчика:** возврат с типом `mismatch_tz` или `critical` обнуляет счётчик «задач без возврата».

### Типы ошибок при проверке

| Тип | Описание | Влияет на оплату | Влияет на грейд |
|-----|----------|------------------|----------------|
| `format` | Оформление, орфография, форматирование | Нет | Нет |
| `incomplete` | Не все пункты ТЗ выполнены | Доработка по правилу ниже | Нет |
| `mismatch_tz` | Не соответствует ТЗ принципиально | Доработка + при 3-й — переход | Сброс счётчика |
| `critical` | Критичная ошибка (баги, потеря данных, нарушение ТК/ПДн) | Возврат, оплата 0 | Сброс + минус в историю |

### Правила оплаты и доработки

- **Базовая формула:** `payout = time_limit × rate_по_грейду`. Факт-часы фиксируются только для аналитики.
- **Апелляция лимита:** до `/start_work` ассистент может **1 раз** запросить пересмотр с обоснованием. Модератор решает.
- **При доработке:**

| Номер доработки | Множитель | Действие |
|----------------|-----------|---------|
| 1-я | × 1.0 | Полная оплата после финального принятия |
| 2-я | × 0.8 | −20% от лимита |
| 3-я | transfer | Задача переходит другому исполнителю с полной оплатой ему |

### Правило «не сдал в срок»

- Дедлайн + **grace 2ч** → автоматический возврат в очередь распределения.
- Текущему исполнителю оплата **0**, событие в `audit_log`.
- Счётчик `failed_deadlines_this_month` инкрементируется.
- При **3 за месяц** ассистент уходит на паузу с пересмотром грейда.

### Распределение задач

**Гибрид:** задача публикуется в общий канал на 5–10 мин (тендер). Если за окно никто не взял — fallback на round-robin с таймаутом.

### Peer-review lite

Перед отправкой результата задачи к менеджерам — обязательная взаимопроверка:

1. Ассистент A сдал через `/done`.
2. Бот выбирает B (не A, свободный).
3. B проверяет по чек-листу 5–7 пунктов (хранится в `policies.config.peer_review_checklist`).
4. B жмёт «ок» или «есть замечания» + тип ошибки.
5. «Ок» → пакет идёт менеджерам.
6. «Замечания» → возврат A на доработку.
7. **Оплата B:** 50 ₽ за каждую проверку.

Это **облегчённая** версия. Полная взаимопроверка (4 документа, спор, судья) — фаза R1 в Развитии II.

## Known Unknowns

- Как именно работает текущая HR-воронка (стек, владелец, как достать отклики)
- Где лежит презентация и можно ли её редактировать (добавить QR/ссылку в финал)
- Готовые шаблоны тестовых заданий по направлениям — придумываем сами + накапливаем
- Полный список направлений работы — пока известно: вайбкодинг как основное
- Точные FSM-состояния и переходы кандидата (откуда → куда → по какому событию)
- Где жить продакшн (тип VPS, домен, бюджет) — открытый вопрос для R4
- Реальные показатели OpenClaw на русском (Whisper, Subagents, latency) — тестировать эмпирически когда подключим
- Качество разных моделей OpenRouter для оценки тестов — тестировать на реальных данных в D1

## Out of Scope (v1 = MVP)

- ИИ-оценщик тестов — фаза D1 (Доработка I)
- Личный кабинет ассистента (`/me`, `/stats`, `/money`) — D2
- Шаблонные нотификации — D3
- Авто-пересмотр ставки — D4
- Карточка кандидата для коммуникатора (ИИ-сводка) — D5
- Умное распределение по рейтингу — D6
- Полная взаимопроверка (4 документа, спор, судья) — R1
- Manager Hub отдельный бот — R2
- Multi-brain ИИ-агенты — R3
- Прод-VPS — R4
- Веб-дашборд — R5
- **Сбор реквизитов карты ассистента** — v2, отдельный флоу при первой ЗП
- ИИ-генерация уникальных тестовых заданий — v1.5
- Мобильное приложение — никогда (TG достаточно)
- **Приём заказов от клиентов / общение с заказчиками** — никогда наша зона
- Расчёт налогов, оформление самозанятых, выдача чеков — **никогда не наша зона**
- Голосовые сообщения, TTS-ответы бота, видео-кружочки — v3+
- Анти-фрод (защита от ботов, дублей резюме, накруток) — v2 если станет проблемой
