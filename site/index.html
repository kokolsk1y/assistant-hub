Слайд 1 — Введение

Что мы строим

Telegram-платформа для координации работы команды ассистентов: от первого отклика до закрытия оплачиваемой задачи.

🎯 Цель MVP

Автоматизировать рутинную координационную работу так, чтобы с ростом команды механизм не упирался в одного человека. Сначала — рабочая механика, потом ИИ-обогащение.

⚙️ Технологический стек

  • OpenClaw — мульти-агентный фреймворк
  • Neon Postgres — данные кандидатов, состояния, история
  • OpenRouter — Claude Sonnet 4.6 / Haiku 4.5 / Opus 4.7
  • Python aiogram 3 — Telegram-бот
  • Хостинг: локально на этапе MVP, далее — VPS
Главные темы для обсуждения на созвоне
  • Профиль будущих ассистентов — нужны ли широкие универсалы или фокус на работу с ИИ
  • Кто финализирует библиотеку тестовых заданий
  • Подход к распределению задач (наше предложение: адресные сообщения с кнопками)
  • Объём процедуры взаимопроверки в первой версии
  • Границы того, что платформа делает автоматически, и что остаётся за человеком

Что это значит на практике

🦴 Скелет (зелёное) — TG-бот, база, FSM, очередь, нотификации. Чистая логика, без ИИ. Это первое что мы строим.

💪 Мышцы (оранжевое) — ИИ-агенты, накладываются опционально (пунктирные стрелки). Если OpenRouter упал — переключаемся на запасной режим.

Запасной режим (если ИИ временно недоступен)
  • Анкета → 4 фиксированных вопроса вместо живого диалога
  • Выбор теста → случайно из библиотеки под направление
  • Оценка → задача ставится в очередь для ручной проверки
  • Распределение → по простому правилу round-robin
  • Сводки → шаблонная таблица из базы
Темы для обсуждения по принципу
  • Подходит ли такой подход — сначала ручной режим, потом постепенная автоматизация?
  • В первые недели работы кто-то должен будет вручную закрывать кейсы которые позже автоматизируются. Это приемлемо?
  • Нужен ли инструмент для «отмены/корректировки» автоматических решений ИИ?
Слайд 3 — Что мы делаем по-другому

Не повторяем старый процесс — строим сильнее

У нас есть описание текущего процесса как ориентир. Но это не догма. Платформа — это шанс пересмотреть рабочие практики там, где ручной режим уже не масштабируется.

📐 Что мы делаем по-новому

  • Распределение задач — адресная рассылка с кнопками вместо «кто первый отреагировал в общем чате»
  • Дедлайны и лимиты — фиксируются в боте с автоматическими напоминаниями
  • Метрики ассистентов — собираются автоматически, без ручного подсчёта
  • Согласование графика на неделю — через интерактивные кнопки выбора времени, а не текстом
  • Подбор тестовых заданий — под профиль кандидата автоматически
  • Сводки и отчёты — генерируются по запросу, не пишутся вручную

🤝 Что остаётся как есть

  • Финальное решение по сложным кейсам — за человеком
  • Личное общение коммуникатора с кандидатами
  • Финансовая часть (выплаты, договоры) — вне платформы
  • Контакт с заказчиками задач — вне платформы
Главная мысль

Документы которыми мы поделились — отличный ориентир по содержанию задач и логике процесса. Но вместо того чтобы автоматизировать всё «как сейчас», мы предлагаем переработать те места, где есть боль:

  • «Реакции в общем чате» — заменяем на адресные сообщения
  • Ручной подсчёт часов и ставок — на автоматический
  • «Тестовые задания на бумаге» — на адаптивную библиотеку с подбором
  • «Помню кто что умеет» — на структурированную базу с поиском

На созвоне хотим обсудить какие из этих переработок одобряем, какие оставляем «как сейчас».

Темы для обсуждения
  • Согласны на пересмотр базовых механик, или хотим точнее воспроизвести текущий процесс?
  • Какие из текущих практик считаем «трогать нельзя»?
  • Есть ли вещи которые в документах не описаны, но обязательно должны быть на платформе?

Главное архитектурное решение

Распределение задач: кнопки вместо реакций в чате

Один из ключевых вопросов на созвон. Наша позиция — отказаться от классической «кто первый отреагировал, тот взял» в пользу адресной рассылки с кнопкой «Принять».

flowchart TB
    T[Новая задача готова]
    T --> SEL{Как распределяем}
    SEL -->|классический подход| CH[Пост в общий чат]
    SEL -->|наше предложение| AI[Система выбирает
подходящего ассистента]
    AI --> PUSH[Бот шлёт в личку
с кнопками Принять / Отказ]
    PUSH --> ANS{Ответ за заданное время}
    ANS -->|принял| W[В работе]
    ANS -->|отказ или молчит| NEXT[Следующий ассистент]
    NEXT --> PUSH

Почему адресная рассылка с кнопкой лучше

  • Балансировка нагрузки — не «кто первый успел», а кто свободен и подходит по профилю
  • Качественный выбор — учитываем рейтинг, текущую загрузку, специализацию
  • Прозрачная история — видно кому предложили, кто отказался, на ком в итоге
  • Не зависит от «онлайна» — кандидат низкого уровня не уведёт задачу высокого только потому что был онлайн
  • Безболезненный рост команды — при росте до десятков ассистентов общий чат превращается в шум
Темы для обсуждения по этому решению
  • Подход с адресной рассылкой и кнопками — подходит?
  • По какому критерию подбирать первого кандидата (по графику, по рейтингу, по специализации)
  • Сколько ждать ответа на «Принять» перед переходом к следующему
  • Что делать если никто не взял задачу — эскалация куда
  • Стоит ли оставить общий чат для анонсов (без распределения)
Этап после сдачи задачи

Взаимопроверка (ревью)

Согласно методике, каждая задача проходит проверку другим ассистентом. Это даёт дополнительный контроль качества.

flowchart TD
    S[Исполнитель сдаёт
4 документа]
    S --> R[Назначаем ревьюера]
    R --> CHECK[Ревьюер ищет
умышленные ошибки]
    CHECK --> FOUND{Все умышленные
ошибки найдены}
    FOUND -- нет --> BAD[Ревью некачественное
назначаем другого]
    BAD --> R
    FOUND -- да --> REAL{Есть случайные
ошибки}
    REAL -- нет --> OK[Задача принята
оплата по полной ставке]
    REAL -- да --> DISP[Спор
исполнитель vs ревьюер]
    DISP --> JUDGE[Судья — третий участник]
    JUDGE --> OK
    JUDGE --> PARTIAL[Принята с замечаниями
пониженная ставка]

Как работает

  • Исполнитель готовит 4 документа: ТЗ, чистовик, версия с умышленными ошибками, ключ-подсказка
  • Ревьюер видит только ТЗ + версию с ошибками. Должен найти умышленные
  • Если нашёл все умышленные — проверка качественная, оценивает реальные ошибки
  • Если нет — назначается другой ревьюер
  • Спор разрешает третий участник
Темы для обсуждения
  • Действительно ли ревью применяется к каждой задаче или есть исключения для мелких
  • Время ревью входит в общий лимит задачи или это отдельный лимит
  • Как выбирать ревьюера — случайно, по очереди, любой свободный
  • Что делать когда нет свободных ревьюеров
  • Роль судьи — это всегда другой ассистент или может быть человек со стороны платформы
  • Подготовка 4 документов на каждую задачу — заметная нагрузка. Шаблонами в боте можем упростить
